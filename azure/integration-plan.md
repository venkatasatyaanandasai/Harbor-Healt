# Integration hand-off — Community Health and Donor Platform

## Backend
- Project: `services/api`
- Run: `npm run dev -w @health/api` (port `4000`)
- Build: `npm run build -w @health/api`
- Health: `GET /health`
- Demo fixtures live only in `services/api/src/store.ts`; demo in-memory storage is not production persistence. Production API workflows fail closed with `503`.

## Frontend
- Project: `services/web`
- Run: `npm run dev -w @health/web` (Vite; port `5173`, host enabled)
- Build: `npm --prefix services/web run build`
- API seam: `services/web/src/api/index.ts`; set `VITE_API_URL` to backend origin.
- UI already calls the Express API. No frontend mock client, mock datasets, duplicate API types, or Mock State Switcher files exist.

## API route inventory
- `GET /health` — public liveness/config status
- `GET /api/health` — public API liveness
- `POST /api/auth/demo-login` — demo only; selects a synthetic profile
- Authenticated: `GET /api/me`
- `GET|POST /api/appointments`
- `GET|POST /api/medications` (POST: clinician/administrator)
- `GET /api/records`
- `GET|POST /api/messages`
- `GET /api/admin/users` (administrator)
- `GET /api/catalog`
- `POST /api/checkout` (demo-only; no order/payment)
- `GET /api/donors/matches` (clinician/administrator/donor)
- `GET|POST /api/donors/profile` (donor; own profile only)
- `GET /api/assistant/status` and `POST /api/assistant/chat` (authenticated, non-diagnostic educational assistant; optional Azure OpenAI provider)
- `GET|POST /api/blood-requests` (POST: clinician/administrator)
- `GET /api/education`

## Data and files
- Structured store: PostgreSQL. `services/api/src/storage.ts` has the pool boundary; `DATABASE_URL` is required in production configuration.
- Files: Azure Blob Storage boundary in `services/api/src/storage.ts`; `AZURE_STORAGE_CONNECTION_STRING`, `AZURE_STORAGE_CONTAINER`.
- Create PostgreSQL schema migrations under `services/api/migrations` (or document an alternative migration directory/tool). **Create NO seed data.**
- Never load demo fixtures into production. Implement durable repositories and resource/clinic authorization before enabling production workflows.
- Donor name and phone are sensitive profile fields. Keep them out of match/search responses; production storage requires reviewed encryption, access controls, retention, and audit policies. The current demo keeps profiles in process memory only and must not contain real donor contact details.
- Assistant messages are not persisted by the app. When Azure OpenAI is configured, chat content is sent to that resource; review data processing, retention, privacy, and security settings before using real patient data. Scripted demo replies are not generated by an AI model.

## Shared types
- `packages/shared/src/index.ts`, package alias `@health/shared`.

## Services and scope
- Essential: React/TypeScript + Fluent UI v9 frontend, Express/TypeScript API, PostgreSQL structured persistence, Azure Blob record/file storage, authentication and least-privilege access.
- Essential workflows: role dashboards (patient, caregiver, clinician, administrator, donor), appointments, medication reminders, records/results, care-team messages, clinic administration, demo-only medicine/wellness catalog checkout, donor registration/request matching, educational self-care and urgent-care guidance only.
- Enhancement: no AI symptom recommendation is implemented. If considered later, constrain to separately reviewed educational material; no diagnosis or prescription.
- Demo mode: synthetic fixtures and process-memory data only, distinct from production config. Checkout is a confirmation only.

## Before production
- Production region/jurisdiction, identity provider, hosting topology, data retention/consent/audit/incident controls, file access policies, and qualified regulatory/security review remain undecided. Do not claim compliance or production readiness.
